# BroadcastManager presentation, message transport and lifecycle hooks

This is a new local compatibility patch authored for the Shabbat upgrade. It is independent of the historical MadelineProto cancellation patch. It adds optional per-instance presentation callbacks to `wizardloop/broadcastmanager` 3.2.2 at commit `f2792a383416b66bb68e55f09414563e540538d6`.

The exact pinned [upstream source](https://github.com/WizardLoop/BroadcastManager/blob/f2792a383416b66bb68e55f09414563e540538d6/src/BroadcastManager.php) was downloaded and byte-matched against the Composer-installed source on 2026-10-13. `baseline/BroadcastManager.php` retains that source and its WizardLoop copyright/AGPL notices. `reviewed/BroadcastManager.php` contains the reviewed resulting source; the unified diff and manifest fix the exact version, commit and source/output/artifact SHA-256 hashes. Both sources are part of the corresponding-source offer. The library's license remains its upstream AGPL license.

`setStatusFormatter(?callable)` receives `(string event, array context): string`. Events are `starting`, `progress`, `pause`, `resume`, `cancel`, and `last_data`. The context includes the default upstream caption. Progress additionally supplies operation type/ID, counters, pending/success totals, rate, progress bar, pause/cancel/done flags and final status; queue contents, recipient IDs and in-flight peer details are excluded. Returned text must be nonempty valid UTF-8 within Telegram's UTF-16 text limit. Set the callback to null to restore exact upstream output.

`setStatusControlsFormatter(?callable)` receives the translated default controls and the bound operation ID/type/pause flag. The application adapter returns native colored MTProto buttons while preserving each original `bm:pause/resume/cancel:<id>` callback. Callback authorization and operator role verification remain the application handler's responsibility. The hook itself performs no RPC.

The application `BroadcastStatusFormatter` uses the same six language catalogs as the private UI for initial captions, complete progress counters, status and controls. Each manager gets its operator's language instance. A current structured `last_data` state can be rendered in the selected locale. A legacy text-only summary cannot reliably be retranslated or reconstructed; it receives an explicit localized recovery notice, and the original dependency file remains available for operator review. The application's structured operator progress/audit view remains available separately.

With all hooks unset, upstream status text, controls and message dispatch remain unchanged. All launched queue and progress futures are now retained and joined before their owner returns. The optional runtime hook enables cancellation-aware sleeps, authorization checks and zero SDK flood-wait limits; the dependency retains its own bounded attempt counter and per-peer retry deadlines. BroadcastManager internal files remain separate third-party state, documented in `docs/BACKUP_RESTORE.md`.

Run `php scripts/apply-patches.php` followed by `php scripts/verify-patches.php` before startup. Composer install/update scripts and the Docker build use these same strict checks. For `composer install --no-scripts`, run both commands explicitly before launching the bot. Never patch an active bot installation. A shared active writer lock prevents modification. Builds read the bundled immutable diff and baseline; they do not download a patch or regenerate one.

The generic `PatchManager` accepts only approved package version/commit and exact source hashes. A pristine approved file is patched atomically and verified; an approved already-patched file succeeds unchanged. Missing patch, wrong version, unknown/partial source, missing/modified baseline, artifact hash mismatch or active writer stops the build. No broad regex/sed replacement or silent fallback is used during installation.

`tests/BroadcastPatchTest.php` exercises clean/repeated installation and verification, wrong version/commit, unknown/partial source and an active writer. It invokes the actual installed patched class's private formatters through reflection without constructing a Telegram API, validates default compatibility, all six localized counters/status/control IDs/styles, per-instance isolation, invalid formatter output, and last-summary handling including a numeric-only operation ID. No broadcast, remote peer mutation or real Telegram status update was used. Native colors/live editing still require a staging Telegram check.

`generate-artifacts.php` is a development-only artifact generator with fixed baseline and previous-source hashes. Maintainers first edit and review `reviewed/BroadcastManager.php`; the generator parses that PHP source and generates exact unified diffs and manifest hashes without changing it. Updating the reviewed patch requires regenerating the unified diff, reviewing it and recording new output/diff hashes in the manifest; builds never execute this generator. Future library versions need a new source/behavior review before being approved.

The unified diff represents empty context lines as an empty removed/added pair. This is standard unified-diff syntax with unchanged old/new hunk counts and identical resulting source; it prevents patch-file context markers from becoming trailing-whitespace violations when the artifact is added to Git. Installer tests verify the exact approved output SHA-256 after applying this representation.


## Message transport hook and dev.3 transition (2026-10-15)

The combined reviewed patch additionally exposes `setMessageTransport(?callable)`. Its per-instance callable receives `(string method, array parameters): mixed` for `sendMessage`, `sendMedia`, `sendMultiMedia` and `editMessage`. All six original message dispatch sites, including albums, ordinary text/media, editing and progress/status messages, use this boundary. Pin, unpin and deletion RPCs remain native. No recipient, random ID, retry limit, media, entity, button or album parameter is dropped by the dependency hook. The application uses its Madeline gateway to decorate these messages and enforce the same native entity/button compatibility behavior as the rest of the bot.

A null hook calls the same native namespace method with the same single parameter array as upstream. Resetting it to null restores that dispatch. The hook does not catch exceptions, convert cancellation into success, add retries or share callable state between instances. The existing upstream callers retain their own retry/status-error policies.

The exact dev.3 patched output is preserved under `previous/dev3/BroadcastManager.php` with SHA-256 `3d9425f7911b12c69faae5e87954db134dc3fb7c2f7d654a72f972ebeb84e424`. The manifest's approved intermediate entry pins this source, its bundled `dev3-to-transport-hooks.patch`, and both hashes. Clean upstream source and that exact previous output can be upgraded offline to the same combined reviewed output. Verification alone rejects the previous output until an explicit installation step runs. Unknown, partially changed or modified previous output fails closed.

All approved intermediate source/diff hashes and resulting output are validated even when the installed file is already current. Transition application uses the same shared application writer lock, second source check, complete PHP parse, output hash and atomic file replacement as clean installation. It never changes a running installation. Composer, Docker and the documented `--no-scripts` procedure keep using `apply-patches.php` and `verify-patches.php`; no network patch download occurs.

The expanded tests cover clean and previous-patched installations, repeat application, verify-only rejection of the old output, active writer refusal, modified transition artifacts and per-instance hook behavior for all four native message methods. An isolated child process loads the actual reviewed library with a small local API namespace shim to prove null-hook dispatch and resetting the hook without constructing MadelineProto or connecting to Telegram. Clone-byte tests include the previous source and transition. Real Telegram delivery and visual rendering remain staging checks.

`generate-artifacts.php` regenerates all three unified diffs and their manifest hashes from the reviewed PHP source and immutable baseline/dev.3/dev.8 inputs. This remains a development-only tool; installation never regenerates patches.

## Runtime lifecycle and dev.8 transition (2026-10-16)

`setRuntimeGuard(?callable, ?Amp\Cancellation)` is an optional per-manager hook. The application's guard is local and synchronous: shutdown, current operator capability, and the current creators of scheduled jobs are checked without calling Telegram or a calendar provider. Its cancellation token is shared by the application and cancelled on shutdown.

When enabled, every worker iteration and every message/pin/unpin/delete RPC boundary checks the guard. Native RPCs receive that cancellation token and `floodWaitLimit=0`; message adapter calls retain the token and the application's gateway also forces zero while preserving native RPC errors for the manager's per-peer retries. Sleeps become cancellation-aware. A false authorization guard cancels the remaining queue and records a cancelled operation. An external `CancelledException`, including a timeout or intentional cancellation, retains its identity and propagates after children drain; it is not retried as an ordinary failed recipient.

The manager retains every queue and progress future. Completion and shutdown wake internal sleeping children, join all of them and release the internal references. The local wakeup exception is recognized by object identity only; it cannot swallow arbitrary cancellation. In-flight accepted Telegram requests remain subject to Telegram's outcome, and cancellation cannot recall a message already accepted. Scheduled cancellation is recorded as cancelled with a partial-outcome notice, never replayed automatically as a fresh broadcast.

The application invokes permissions, notifications and scheduled broadcast work in independent native cron loops. Scheduled broadcasts have a non-overlap guard. An empty/future native queue does not cause a permission scan; a due batch checks permission priority before starting and current creator authority again after that potentially asynchronous check. The permission scheduler remains able to run while a native broadcast waits for a reply or a per-peer retry deadline.

The exact dev.8 reviewed source is preserved as `previous/dev8/BroadcastManager.php` (`08db35c271f671041257ebe79d1010cdd7c33c4d5868e4553c78612f9e8bf0f3`). The manifest adds its immutable `dev8-to-runtime-lifecycle.patch` transition. The original 3.2.2 baseline, commit and copyright/license notices are unchanged; the reviewed source, all previous sources and all three diffs are included in the corresponding-source archive.

Offline tests run the actual installed worker and progress methods with controlled futures and without a Telegram API: suspended broadcast plus independent close, 1,000 queued targets cancelled on shutdown, deliberate cancellation identity, role revocation, progress wakeup/join, 1,000 empty/future scheduler cycles with no permission scans, reentrancy, creator attribution and clean/dev.3/dev.8/repeated/partial/unknown patch installation. Live Telegram delivery, real flood quotas and process shutdown during an already accepted request remain staging checks.

`setRuntimeAdmission(?callable)` optionally wraps each actual send/edit/delete/unpin/self-destruct operation. The application supplies one cancellation-aware FIFO shared by manual and scheduled managers: only one native operation can run at once, and a waiting operator's capability and scheduled creator authority are checked again after admission. Shutdown aborts queued admissions without starting them. This caps application native workers at one operation's limit (UI 20, dependency maximum 30), rather than multiplying the cap by the number of operators. The optional hook is unset for upstream consumers.

With runtime hooks enabled, only the latest 128 fully drained completed progress entries remain in each native in-memory index. Active, paused, in-flight and still-joining entries are preserved. Persistent broadcast history and message IDs are not removed; an old completed inline control may report that its operation is no longer active. Tests cover 40 concurrent FIFO admissions with maximum active count one, 40 queued admissions cancelled behind one active operation, all six operation wrappers, cancellation precedence and pruning that preserves active/in-flight/joining entries.
